Anarlog `2.0.0` replaces our Tauri and system WebView desktop frontend with a single-process Rust application built on GPUI (`apps/desktop-gpui`).

[Anarlog](https://anarlog.so) is an MIT-licensed, open-source, local-first AI meeting notetaker backed by local SQLite, with Markdown available as an export format rather than canonical storage. Because a meeting notetaker has to stay open all day alongside video calls, system audio capture, and optional local models, a multi-process browser runtime sitting at around 1 GiB of memory was the wrong foundation.

Across an identical 5,000-note local SQLite fixture on fresh macOS, Linux, and Windows VMs, moving from shipping `1.4.35` (Tauri + system WebView) to GPUI cut cold launch times by `91.3%` to `94.4%` (`11.4x` to `17.7x` faster) and dropped idle memory by `83.8%` to `97.5%`. This post documents the full benchmark dataset, environment caveats (including a software-Vulkan resize CPU regression on Linux), two pre-release regressions the harness caught before `2.0.0` shipped, and binary measurements from the signed Apple Silicon production release.

## Methodology and test environments

The ANLG-320 fresh-VM audit ran on November 18-19, 2026 against two builds:

- **Baseline (`1.4.35`)**: Shipping signed Anarlog `1.4.35` using Tauri and each OS's system WebView.
- **Candidate (`apps/desktop-gpui`)**: Optimized GPUI build compiled with Rust `1.98.1` (`PR #8235`, commit `83f2caa64e7674cc1511de7fbd1c277b26334f4e`, paired with Linux fixes `#8222`/`#8224` and Windows fix `#8226`).

Every test used an identical pre-seeded local SQLite database:

- `5,000` regular notes (`300-1,500` words of TipTap JSON each)
- `2,500` AI summaries
- `1` stress-test note containing `20,000` words
- `300` contacts, `50` folders, and `2,000` calendar events

All runs used Light theme, `100%` zoom, a `1280x800` window, signed-out state, and cloud sync disabled. Each scenario ran `1` warmup iteration followed by `5` alternating runs between baseline and candidate, except where explicitly noted (`n=1` empty launch, `n=100` or `20` note switches, and the macOS visible-idle `n=4` / `n=5` CPU bound).

| Platform | VM and hardware | Graphics and WebView stack | Memory metric | Process model |
| --- | --- | --- | --- | --- |
| macOS VM | `macOS 26.6.2` (`25G83`), Apple M4 Pro Virtual (12 cores, 16 GiB RAM) | Apple Paravirtual Metal vs WKWebView | `proc_pid_rusage` `phys_footprint` | Tauri multi-process vs `1` GPUI process |
| Linux VM | KVM x86-64, Ubuntu `22.04.5`/`24.04.5`, 8 vCPU Xeon, 31 GiB RAM | X11/KDE KWin, Mesa `25.2.8` `lavapipe` Vulkan vs WebKitGTK `2.52.6` (`WEBKIT_DISABLE_DMABUF_RENDERER=1`) | cgroup PSS (`/proc/<pid>/smaps_rollup`) | Tauri + WebKitGTK processes vs `1` GPUI process |
| Windows VM | Windows Server `2022` x64 (`20348`), Xeon Platinum `8559C` (8 cores, 32 GiB RAM) | Microsoft Basic Render Driver D3D 11.1 vs WebView2 `157.0.4341.60` (`D3D10Warp.dll`) | Job Object Private Working Set | `7-8` WebView2 processes vs `1` GPUI process |

Two measurement rules matter when reading these tables:

1. **Compare within an OS, not across OSes.** `phys_footprint`, cgroup PSS, and Private Working Set measure different slices of physical and shared memory. They are consistent for `1.4.35` vs GPUI on the same host, not directly comparable between macOS, Linux, and Windows.
2. **Linux and Windows VMs used CPU software rendering.** Mesa `lavapipe` on Linux and Microsoft Basic Render Driver (`D3D10Warp.dll`) on Windows execute GPU commands on the CPU. That penalizes continuous full-window redraws in GPUI more than hardware GPUs would.

## macOS VM results

On `macOS 26.6.2` (`25G83`) with Apple Paravirtual Metal, GPUI reduced memory usage by `93.3%` to `95.4%` across note and idle workloads on the 5,000-note fixture and stayed at `52.2 MiB` to `55.4 MiB` during 10-minute idle runs.

Two details stand out in the macOS run. First, closing `1.4.35` to the menu bar tray did not release WKWebView memory; its median `phys_footprint` stayed at `961.3 MiB` and climbed to `1,528.8 MiB` by the end of the 600-second window, compared to `55.4 MiB` in GPUI. Second, GPUI's `phys_footprint` rose from its `52-80 MiB` range up to `333.0 MiB` during 5 seconds of continuous window resizing due to Metal surface allocations, though it still stayed `75.3%` below `1.4.35` (`1,349.7 MiB`) while using `83.2%` less CPU (`1.630 s` vs `9.704 s`).

## Linux VM results and the software-Vulkan resize caveat

On Linux under X11/KDE KWin, WebKitGTK struggled both with memory growth in large documents and with save durability on exit, while GPUI hit a clear CPU regression during continuous resizing under software Vulkan (`lavapipe`).

| Cold launch (5,000-note list) | CPU / PSS | 11.110 s / 1,480.7 MiB | 0.478 s / 247.7 MiB | -95.7% / -83.3% |

| Note switching (20 opens) | Latency | 509.2 ms | 147.4 ms | -71.1% (3.5x faster) |
| Note switching (20 opens) | CPU / PSS | 30.393 s / 1,650.8 MiB | 22.679 s / 267.3 MiB | -25.4% / -83.8% |

| 20,000-word typing (500 chars, mid) | CPU / PSS | 88.308 s / 4,033.2 MiB | 56.033 s / 270.0 MiB | -36.5% / -93.3% |
| 20,000-word typing (500 chars) | Full edit verified after quit | 0/5 | 5/5 | Verified persistence |

| 5s continuous resize | PSS | 1,709.7 MiB | 258.7 MiB | -84.9% |

Two Linux findings deserve closer inspection:

- **Continuous resize CPU regression (`+48.1%`)**: GPUI consumed `9.844 s` of CPU over the 5-second resize test vs `6.648 s` for `1.4.35`, even though PSS dropped `84.9%` (`1,709.7 MiB` to `258.7 MiB`). Profiling showed why: `53.7%` of GPUI's CPU time went to Mesa `llvmpipe-*` JIT threads and another `32.4%` went to `libvulkan_lvp.so`. Without a hardware GPU in the headless VM, every resized frame was rasterized on the CPU by Mesa `lavapipe`. On desktop Linux systems with hardware Vulkan drivers, that rasterization work leaves the CPU.
- **Large-note memory ballooning and data loss in `1.4.35`**: Typing 500 characters into the 20,000-word note pushed WebKitGTK's PSS past 4 GiB (`4,028.0 MiB` at end, `4,033.2 MiB` mid-document) vs `270.3 MiB` / `270.0 MiB` in GPUI. Worse, `1.4.35` failed post-quit SQLite verification in `0/5` runs on Linux, which led directly to the `1.4.36` fix described below.

## Pre-release regressions the harness caught

Running automated cross-platform scenarios before tagging `2.0.0` surfaced two real bugs that would have shipped without the harness.

### 1. GPUI wheel scroll stalls (`1,014` events)

During the `1,014`-event wheel scroll test, the initial GPUI candidate took `101.37 s` to complete on Windows vs `9.28 s` on `1.4.35`, and `128.2 s` vs `89.9 s` on Linux. On macOS, Instruments traced an approximately `18 s` `CAMetalDisplayLink` stall during rapid scroll bursts.

One subtlety in the Windows baseline made the raw timing misleading until we inspected the captured frames: `1.4.35` finished the event stream in `9.28 s` partly because `70.14%` of its captured frames showed blank white bands while WebView2 skipped painting, whereas GPUI rendered `0.00%` blank-band frames. Even accounting for complete frames, GPUI's scroll handling was doing far too much redundant layout and display-link work per wheel event.

We fixed the underlying wheel-scroll pipeline in **PR `#8236`**, bringing the Windows `1,014`-event test down from `101.37 s` to `14.9 s`, and calibrated platform scroll steps in **PR `#8242`** (`100px` and `86px` wheel-notch increments) before `2.0.0` shipped.

### 2. Save-on-quit data loss in shipping `1.4.35`

When the harness reopened the SQLite database after each `20,000`-word typing run and checked whether all 500 typed characters survived process exit, shipping `1.4.35` failed `0/5` full edits on Linux and dropped characters on partial edits on macOS. GPUI passed `5/5` on Linux.

In the Tauri app, closing the window or quitting immediately after rapid typing could terminate before the debounced ProseMirror-to-SQLite flush completed. We fixed the flush-on-quit path in **PR `#8238`** and shipped it to Tauri users in **`1.4.36`**, which also acts as the bridge release for the `2.0.0` updater cutover.

## Signed production Apple Silicon artifacts (`1.4.36` vs `2.0.0`)

VM tests show runtime behavior under controlled fixtures. To verify what actually ships to users, we inspected the signed production Apple Silicon `.dmg` installers and unpacked `.app` bundles for `1.4.36` (Tauri) and `2.0.0` (GPUI) on an Apple M5 Max (`48 GiB`, `macOS 27.0.1`), both code-signed by `Fastrepl, Inc. (6SLY7V277V)`.

| Artifact / Metric | 1.4.36 (Tauri) | 2.0.0 (GPUI) | Delta |
| --- | --- | --- | --- |
| Signed `.dmg` size | 213,859,301 B (203.9 MiB) | 178,515,118 B (170.2 MiB) | -16.5% |
| Unpacked `.app` size | 490,304 KiB / 501,984,504 B (478.7 MiB) | 424,628 KiB / 434,730,086 B (414.6 MiB) | -13.4% |
| Main binary (`Contents/MacOS/anarlog`) | 351,841,040 B (335.5 MiB) | 284,586,624 B (271.4 MiB) | -19.1% |
| Linked dynamic libraries | 76 (includes `WebKit.framework`) | 70 (0 `WebKit` or `JavaScriptCore`) | -6 dylibs |
| `Resources` / `Frameworks` / `anarlog-cli` | 122,248 KiB / 628 KiB / 23,625,360 B | 122,248 KiB / 628 KiB / 23,625,360 B | Unchanged |

The shipped `2.0.0` Apple Silicon `.dmg` (`SHA-256`: `3a50d4d4e96effba2d4b311ee7bf9d784f6f38c3acfb3f92cf65d1f1b9afc05b`) removes all `WebKit` and `JavaScriptCore` linkage from the main executable while keeping the CLI binary (`anarlog-cli`, `23,625,360` B), bundled resources (`122,248 KiB`), and frameworks (`628 KiB`) identical.

Running the signed `2.0.0` `.app` directly in an isolated `--profile` across `n=5` launches on that Apple M5 Max measured:

- **First window painted**: `256.5 ms` median (`247.7-261.6 ms` across warm runs; cold run 1 took `2,429.1 ms`).
- **Memory**: `62.0 MiB` `phys_footprint` (`138.7 MiB` RSS, `234.0 MiB` peak).
- **Processes and idle CPU**: `1` process (`0` WebKit helpers), `28` threads, and `0.16%` idle CPU.

## Limits of these benchmarks and next steps

These measurements isolate UI rendering, search, editor typing, and local SQLite persistence in a signed-out, sync-off configuration. They do not measure audio capture threads, live transcription throughput, local LLM inference, or encrypted CloudSync traffic, all of which add their own CPU and memory profiles when active. On Linux and Windows, VM software rasterization (`lavapipe` and Microsoft Basic Render Driver) also distorts resize and heavy-paint numbers relative to physical GPUs.
